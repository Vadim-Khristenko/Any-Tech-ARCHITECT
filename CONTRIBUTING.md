## Быстрый старт

```bash
# 1. Форкните репозиторий на GitHub и склонируйте свой форк
git clone https://github.com/<вы>/Any-Tech-ARCHITECT.git
cd Any-Tech-ARCHITECT

# 2. Установите зависимости (рекомендуется bun, npm тоже работает)
bun install

# 3. Запустите dev-сервер
bun run dev
```

| Команда | Что делает |
|:--|:--|
| `bun run dev` | Dev-сервер с HMR |
| `bun run build` | Продакшн-сборка, заглушки для ботов, sitemap, robots |
| `bun run preview` | Просмотр собранного проекта |
| `bun run test:run` | Однократный прогон тестов |
| `bun run test` | Тесты в watch-режиме |
| `bun run typecheck` | Проверка типов без сборки |
| `bun run og` | Пересборка OG-изображений и превью для GitHub |
| `bun run kit` | Страница бренд-кита, вне продакшн-сборки |
| `bun run domains` | Работа с базой доменов-доноров |
| `bun run configs` | Генерация матрицы конфигов XRay и прогон её через настоящие ядра |

Сервер из `tools/awg-serve` собирается отдельно, через cargo:

```bash
cd tools/awg-serve
cargo test          # разбор путей, обход каталога, MIME-типы
cargo build --release
```

Зависимостей у него нет и быть не должно: он едет в релизном архиве, поэтому
обязан собираться на голом тулчейне. Edition 2024, минимум Rust 1.85. В CI
бинарь собирается нативно на раннере каждой ОС, не кросс-компиляцией.

## Стек

Vue 3 (`<script setup>`), TypeScript, Vite, Vitest, `lucide-vue-next` для
иконок, `pako` для кодека `vpn://`. CSS-фреймворка нет — обычный CSS с
кастомными свойствами.

## Структура проекта

```
src/
  engines/       по каталогу на движок, оба под общим интерфейсом
    awg/         AmneziaWG: генератор, правила, парсер, симулятор пакетов
    xray/        XRay: REALITY, транспорты, FinalMask, привязки полей
    registry.ts  что вообще есть за движки
  shared/        то, что честно общее: RNG, x25519, домены, клиенты, находки
  composables/   реактивные обёртки над движками
  components/    общие компоненты
  views/         страницы
  i18n/          каталоги, рантайм и SEO-метаданные по локалям
  data/          контент: FAQ, ченджлог, ссылки поддержки
  workers/       batch-генерация вне основного потока
assets/
  kit/           бренд-кит: токены и примитивы
  main.css       точка входа стилей
scripts/og/      генератор OG-изображений
scripts/configs.ts  матрица конфигов XRay против реальных ядер в Docker
tools/awg-serve/ статический сервер на Rust, попадает в релизный архив
```

**Правила архитектуры**

- Движок не знает про Vue и, где возможно, про i18n. `awg/generator/render.ts`
  принимает переведённые строки аргументом, а не импортирует каталог, — поэтому
  он работает и в воркере, и в тестах.
- В `shared/` попадает то, чем действительно пользуются оба движка. Если код
  нужен одному — его место в этом движке, даже если выглядит общим.
- Число, которое знают два места, рано или поздно разойдётся. Смещения размеров
  сообщений AmneziaWG были записаны трижды, и дважды неверно; теперь они
  выводятся из размеров сообщений в `engines/awg/messageSizes.ts`. Если
  константу приходится повторять — выносите её.
- `composables/` возвращают `ref`, `computed` и экшены.
- `views/` содержат шаблон, scoped-стили и минимум логики.

## Бренд-кит

Все токены и примитивы — в `assets/kit/`. Своих цветов, теней и радиусов в
компонентах быть не должно: если нужного примитива нет, добавьте его в кит, а не
рядом с местом использования.

`bun run kit` открывает страницу со всем, что в ките есть, — она собирается
отдельным конфигом и в продакшн-сборку не попадает.

Тема одна на два режима: `light-dark()` и `color-mix(in oklab, …)`, акцент
хранится каналами RGB. Поэтому новый цвет почти никогда не нужно задавать
дважды.

## Стиль кода

**TypeScript** — строгая типизация; `any` только если иначе никак. Для форм
объектов предпочтительны интерфейсы. Код движка должен оставаться чистым. JSDoc
на экспортируемых функциях объясняет *почему*, а не пересказывает сигнатуру.

**Vue** — только `<script setup lang="ts">`, без Options API. Всегда
`<style scoped>`. `ref()` для примитивов, `reactive()` для объектов.
`PascalCase` для компонентов, `camelCase` для остального.

**CSS** — используйте токены из `assets/kit/tokens.css`. Брейкпоинты: 960px,
768px, 480px. Для всего движущегося учитывайте `prefers-reduced-motion`.

**Форматирование** — четыре пробела в `.vue`, два в `.ts`; точки с запятой;
висячие запятые (trailing commas).

## Локализация

Каталоги переводов лежат в `src/i18n/locales/`. Русский — источник истины,
английский типизирован по нему, поэтому **пропущенный перевод ломает сборку**:
сначала добавьте ключ в `ru.ts`, затем в `en.ts`.

Ключи плоские, с точками (`gen.export.copyConf`), сгруппированы по областям.
При добавлении текста в интерфейс:

- Не пишите строку прямо в шаблоне — только `t("some.key")`.
- В атрибутах нужен биндинг: `:title='t("some.key")'`, а не `{{ }}` —
  интерполяция в значении атрибута невалидна.
- Подстановки — через `{name}`, значения передаются вторым аргументом.
- Для количеств используйте формы множественного числа: в русском их три
  (`one`/`few`/`many`), в английском две.

Перевод — не подстрочник. Если в русском варианте фраза работает за счёт
порядка слов, в английском её стоит перестроить. Один раз английский текст уже
сказал ровно противоположное русскому именно потому, что переводился дословно.

Метаданные страниц вынесены отдельно, в `src/i18n/seo.ts`, и используются и
роутером, и генератором заглушек при сборке — так они не могут разойтись.

## Изменения в протоколе

Одна вещь, которую стоит знать перед правкой генератора: **документация
отстаёт от реализации.** У AmneziaWG она на момент написания описывает 2.0,
тогда как `amneziawg-go` уже на 3.0.1. У Xray-core документация отстаёт от
релизов примерно так же.

Если вы меняете то, как параметры генерируются или проверяются, ссылайтесь на
исходники — файл и строку в `amneziawg-go`, `amneziawg-tools` или `Xray-core`, —
а не на документацию. Часть правил в этом коде существует только потому, что так
написано в реализации: например, порог S1–S4 ≥ 12 при защите заголовков,
которого нет ни в одной документации.

Для XRay есть проверка посерьёзнее тестов: `bun run configs` генерирует матрицу
конфигураций и скармливает каждую **ядру той версии, для которой она сделана**.
Одно ядро на все версии не доказывает ничего — неизвестные ключи молча
игнорируются. Так нашлись три ошибки, которые юнит-тесты пропустили.

Новое поведение протокола стоит закрывать тестом на инвариант, а не только на
удачный сценарий. И осторожнее с «упрощёнными проверками»: тест, который
считает одно, а утверждает другое, — это не тест, а комментарий.

## Pull request

Ветку создавайте от `main`:

```bash
git checkout -b feature/my-change
git checkout -b fix/issue-42
```

| Префикс | Для чего |
|:--|:--|
| `feature/` | новая функциональность |
| `fix/` | исправления багов |
| `docs/` | документация |
| `refactor/` | перестройка без смены поведения |
| `test/` | тесты |

Перед открытием PR убедитесь, что `bun run typecheck` и `bun run test:run`
проходят. В описании укажите, **что** меняется и **почему**, и приложите
скриншот, если изменение визуальное.

## Предложения по доменам

База доменов-доноров в `src/shared/domains.ts` поддерживается вручную и требует
проверки. Пользуйтесь шаблонами issue — они спрашивают страну и провайдера,
откуда вы проверяли, и это важно: доступность сильно зависит от сети, а без этих
данных локальную блокировку не отличить от общей.

В базе лежат факты, а не оценки: что за сайт, где хостится, какие у него TLS и
HTTP. Придуманных «статусов» вроде «хороший донор» там нет и не будет — они
устаревают быстрее, чем их успевают править.

> Пожалуйста, не добавляйте домен, который вы лично не проверили из того
> региона, для которого он предназначен.

## Баг-репорты

Пользуйтесь шаблонами issue. Для конфига, который не подключается, важны версия
AmneziaWG или Xray, клиент с его версией и сами параметры.

Отдельно стоит сказать: **разбор кода со ссылкой на исходники upstream — самый
полезный вид issue, какой тут бывает.** Три ошибки — в правилах совпадения
размеров, в тексте про защиту заголовков и в ответе FAQ — были найдены именно
так, чтением, а не воспроизведением. Если вы сверяете этот генератор со своим и
видите расхождение, напишите: скорее всего, правы вы.

> **Никогда не вставляйте приватные ключи.** Удаляйте `PrivateKey`,
> `PresharedKey`, `HeaderProtectionKey` и приватную половину ключевой пары
> REALITY — для воспроизведения они не нужны, а ключ, опубликованный в issue,
> придётся перевыпускать.
